# Contributing

Thank you for contributing to `kuasar-sandbox/orchestrator`.

## Current access model

The organization currently uses a private-fork workflow:

- Contributors can open and triage issues, review changes, and submit pull requests.
- Contributors develop on branches in their own private forks; they do not need write access to the upstream repository.
- Maintainers have upstream write access and are responsible for review, trusted CI execution, and squash merging.
- Direct pushes to upstream `main` are prohibited by project policy.

This model keeps upstream write access limited while the current GitHub plan does not provide enforceable protected-branch rules for private organization repositories.

## Prepare a private fork

Fork the repository to your personal GitHub account, then configure the remotes:

```bash
git clone git@github.com:<your-login>/orchestrator.git
cd orchestrator
git remote add upstream git@github.com:kuasar-sandbox/orchestrator.git
```

Keep your fork's `main` synchronized with upstream:

```bash
git fetch upstream
git switch main
git reset --hard upstream/main
git push --force-with-lease origin main
```

Create a topic branch for every change:

```bash
git switch -c feat/short-description
# edit, test, and commit
git push -u origin feat/short-description
```

Open a pull request from `<your-login>/orchestrator:feat/short-description` to `kuasar-sandbox/orchestrator:main`. Enable **Allow edits from maintainers** when appropriate.

## Pull request requirements

A pull request should:

- have a focused scope and a clear description of the problem and solution;
- link the relevant issue when one exists;
- include or update tests and documentation when behavior changes;
- contain no credentials, private keys, tokens, customer data, or unrelated generated files;
- describe validation already performed and any operational or compatibility risk.

Draft pull requests are welcome for early feedback, but they are not merge candidates.

## CI and merge policy

Fork pull requests must not execute untrusted code on the privileged self-hosted
BMS runner. Their automatic BMS job remains skipped. After completing code
review, a maintainer runs the trusted `main` copy of `bms-e2e.yml` against
GitHub's current PR merge commit. This tests the tree that would be merged,
instead of the fork head in isolation.

Never dispatch the workflow from a fork-authored or temporary CI branch. The
selected workflow ref must be `main`; the reviewed integration commit is passed
separately as `candidate_sha`. The workflow rejects a dispatch unless:

- the selected workflow SHA equals the recorded current `main`/base SHA;
- the supplied PR number, candidate, base, and head still match the current
  upstream pull request and its GitHub-generated merge commit;
- the candidate is a full commit SHA in the upstream repository;
- the candidate has exactly two parents, in order: the recorded base SHA and
  reviewed head SHA; and
- `main` still points to the recorded base SHA when source assembly begins.

Use the read-only `refs/pull/<number>/merge` ref generated by GitHub for a
mergeable pull request. For example, from a clone whose `upstream` remote is
`kuasar-sandbox/orchestrator`:

```bash
repo=kuasar-sandbox/orchestrator
pr=123

base_sha=$(gh api "repos/$repo/pulls/$pr" --jq .base.sha)
head_sha=$(gh api "repos/$repo/pulls/$pr" --jq .head.sha)
git fetch --no-tags upstream "refs/pull/$pr/merge"
integration_sha=$(git rev-parse FETCH_HEAD)
read -r integration_base integration_head extra_parent \
  < <(git show -s --format=%P "$integration_sha")
trusted_workflow_sha=$(git ls-remote upstream refs/heads/main | awk '{print $1}')

test -z "${extra_parent:-}"
test "$integration_base" = "$base_sha"
test "$integration_head" = "$head_sha"
test "$trusted_workflow_sha" = "$base_sha"

gh workflow run bms-e2e.yml \
  --repo "$repo" \
  --ref main \
  -f confirm=run-full-e2e \
  -f pull_request_number="$pr" \
  -f candidate_sha="$integration_sha" \
  -f base_sha="$base_sha" \
  -f head_sha="$head_sha"
```

Record the base, reviewed head, integration, and trusted workflow SHAs plus the
successful run URL in the pull request. Immediately before merging, query the
pull request again and confirm that both `.base.sha` and `.head.sha` are
unchanged. A new base or head commit invalidates approvals and CI evidence and
requires a new integration commit and run. Then squash merge manually.
Auto-merge, merge commits, and rebase merges are not used.

## Review expectations

Be constructive and specific. Authors should resolve review conversations or explain why a requested change is not applicable. Maintainers may close stale, superseded, unsafe, or out-of-scope pull requests with an explanation.
